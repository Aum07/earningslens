# Decisions

Format: date, decision, reason, alternative considered.

## 2026-10-30: Plain JdbcTemplate for vector and keyword search
- **Decision:** do not use the Spring AI PGvector VectorStore. Vector search, full-text search and RRF fusion are written as SQL with `JdbcTemplate`.
- **Reason:** hybrid search needs custom SQL (pgvector cosine, Postgres full-text, metadata filters, per-quarter retrieval), and owning the queries makes the retrieval logic easy to explain and test.
- **Alternative considered:** Spring AI `PgVectorStore`, which handles vector search well but does not cover full-text search or RRF.

## 2026-10-30: Backend generated with Spring Boot 4.1.2 and Spring AI 2.0.1
- **Decision:** latest stable Boot and Spring AI offered together by start.spring.io (through IntelliJ) on 2026-10-30. Configuration in YAML.
- **Reason:** spec section 4 says to use the latest stable pair and pin it.
- **Alternative considered:** Spring Boot 3.5 with Spring AI 1.1, rejected because 3.5 is out of open-source support.

## 2026-10-30: Secrets loaded from a gitignored .env through spring.config.import
- **Decision:** `application.yaml` imports `optional:file:../.env[.properties]` so local runs read OPENAI_API_KEY and DB settings from `.env`. The `prod` profile has no defaults for secrets, so a missing variable stops the app at startup.
- **Reason:** no extra dependency, works the same from IntelliJ and `mvnw`, and Azure supplies real environment variables.
- **Alternative considered:** a dotenv library (not in the locked stack), or setting Windows environment variables by hand (easy to forget, not visible in the repo).

## 2026-10-30: Typed, validated configuration records
- **Decision:** one `@ConfigurationProperties` record per area (LLM, retrieval, rate limit, SEC) with jakarta.validation constraints.
- **Reason:** bad or missing config fails at startup instead of mid-request; model names and tuning values live in config, not code (spec section 4).
- **Alternative considered:** `@Value` on individual fields, which scatters settings and has no validation.

## 2026-11-01: SnakeYAML to read corpus/manifest.yaml
- **Decision:** `ManifestLoader` reads the manifest with SnakeYAML (`org.yaml:snakeyaml`, version managed by Spring Boot) using `SafeConstructor`.
- **Reason:** Spring Boot already ships SnakeYAML to read `application.yaml`, so this adds no new library to the app; declaring it explicitly makes the dependency visible. `SafeConstructor` only builds plain maps, lists and strings, which blocks YAML deserialization attacks.
- **Alternative considered:** Jackson YAML (an extra module, and Boot 4 moved to Jackson 3), or binding the manifest through `@ConfigurationProperties` (mixes data with app config).

## 2026-11-01: Headings in SEC HTML found by bold or underline styling
- **Decision:** `HtmlParser` treats a short block whose text is at least 95% bold or underlined (inline style, `b`/`strong`, or `h1`-`h6`) as a heading. A heading that appears 3 or more times in one document is treated as a running page header and dropped.
- **Reason:** SEC iXBRL filings contain no `h` tags; headings are styled spans. Checked against the real MSFT, GOOGL and META 10-Qs before writing the Java.
- **Alternative considered:** relying on `h1`-`h6` only (finds no headings in SEC filings), or a fixed list of known 10-Q headings (breaks on new companies).

## 2026-11-01: jtokkit for token counting
- **Decision:** count tokens with jtokkit (`cl100k_base`, the encoding of text-embedding-3-small), declared explicitly in the pom at the version Spring AI already uses (1.1.0).
- **Reason:** spec section 4 allows Spring AI `TokenTextSplitter` or jtokkit. The chunker needs exact counts for its own rules (paragraph, then sentence boundaries, speaker turns, overlap of whole sentences), which `TokenTextSplitter` does not offer.
- **Alternative considered:** `TokenTextSplitter`, which splits by token count only and would cut sentences and mix speakers.

## 2026-11-01: Chunks never cross a section, speaker or forward-looking change
- **Decision:** the chunker groups blocks by (section, speaker, forward-looking tag) and packs paragraphs only within a group. Overlap is whole sentences, prose only, never table rows.
- **Reason:** each chunk row stores one `section` and one `speaker`; mixing groups would make those columns wrong and blur citations. Keeping forward-looking text in its own chunks lets eval exclude it cleanly.
- **Alternative considered:** packing across sections for fuller chunks, which gives fewer tiny chunks but wrong metadata.

## 2026-11-01: Speaker labels in transcripts
- **Decision:** a paragraph starts a new speaker turn when it begins with "Name Surname[, Role]:" (2 or 3 capitalised words), is a "Name Surname, Role" line on its own, or starts with "Operator". A short name seen earlier with a role ("Susan Li, CFO") is stored with that role.
- **Reason:** covers all three corpus formats (Alphabet inline, Microsoft capitals, Meta label lines) and rejects false alarms such as "Second:" found in the real transcripts.

## 2026-11-01: Embedding retries in our own code, client retries off
- **Decision:** `EmbeddingService` retries 429, 5xx and network errors with exponential backoff (1s, 2s, 4s, 8s, 16s; max 5 retries) and fails fast on other errors. `spring.ai.openai.max-retries` is set to 0.
- **Reason:** the roadmap asks for our own backoff with a testable "fails twice then succeeds" unit test. With the client's built-in retries (3 by default) left on, one failure could become up to 18 requests.
- **Alternative considered:** relying only on the OpenAI client's built-in retries (simpler, but not visible or testable in our code).

## 2026-11-01: V2 migration adds chunks.forward_looking
- **Decision:** `V2__chunks_forward_looking.sql` adds `forward_looking BOOLEAN NOT NULL DEFAULT false` to `chunks`. V1 stays untouched.
- **Reason:** spec 7.2 step 3 says to keep forward-looking boilerplate but tag it so eval can exclude it later; the V1 schema had no place to store the tag.
- **Alternative considered:** a marker inside `content` (pollutes the embedded text and keyword search), or not storing the tag (loses the option to filter).

## 2026-11-01: Embed before the database transaction
- **Decision:** `IngestionService` hashes, parses, cleans, chunks and embeds first; only then `DocumentStore.store` opens one transaction that inserts the document (JPA) and its chunks (JdbcTemplate batch).
- **Reason:** OpenAI calls can take seconds or fail and retry; holding a database transaction open during them is wasteful and risky. A failed embedding leaves nothing half-written. Duplicate files (same SHA-256) are skipped before any OpenAI call, so a re-run costs nothing.

## 2026-11-01: Section line in every chunk, and E1.9 cleanup rules
- **Decision:** a chunk under a heading gets a "Section: <heading>" line after the "[TICKER | FYyyyy Qn | DOC_TYPE]" header (cut to 200 characters). `TextCleaner` now also removes short repeated tables (page-top tables such as "Table of Contents | Alphabet Inc.") and the cover-page label "(Mark One)".
- **Reason:** the E1.9 sanity check found chunks whose whole body was "None." or "Not applicable." (answers to 10-Q items like "Defaults Upon Senior Securities"). Without the heading these say nothing; with it they answer real questions ("any legal proceedings?") and the embedding knows the topic. It also helps every other chunk: the heading names the topic of the text below it. The same check found Alphabet's per-page header table stored as duplicate chunks.
- **Alternative considered:** deleting tiny chunks (loses real answers) or merging them into the next section (wrong section metadata). Cost of the change: one re-embed of the corpus, about 2 US cents.

## 2026-11-01: Eval dataset format and loader (E2.1)
- **Decision:** `EvalDatasetLoader` reads `eval/dataset.jsonl` one line at a time with Jackson 3 (`tools.jackson`, already in the app through Spring Boot 4, so no new dependency) into a plain Map, then checks it by hand and builds `EvalItem` records. Rules: unknown fields are rejected (catches typos such as `gold_evidnce`); `answerable` must be false only for `unanswerable`; answerable items need at least one quote, unanswerable items none; `multi_quarter` items need evidence from at least 2 periods (period coverage depends on it); quotes are at least 15 characters; question 3 to 500 characters (same as the chat API); ids look like `q001` and are unique. Errors name the file, line, item id and field.
- **`filters` shape:** same as the chat API request in spec 10 (`tickers`, `fiscalPeriods: [{year, quarter}]`, `docTypes`), so an item can be sent to the API unchanged. `null` or missing means no explicit filters.
- **Reason:** clear errors while writing 80 items by hand; letting Jackson bind records directly gives vaguer messages.
- **Alternative considered:** Jackson record binding with `@JsonProperty` (less code, worse error messages), or Jackson 2 (`com.fasterxml`, only present because Spring AI pulls it in).

## 2026-11-01: Dev split has 34 items, 9 of them unanswerable (E2.2)
- **Decision:** 4 extra unanswerable dev items (q031-q034), so dev has 9 unanswerable instead of 5. The test split will have 5 unanswerable instead of 9, so the whole dataset is 84 items with 14 unanswerable (spec 11.1 asks for at least 80 and 15).
- **Reason:** E3.7 tunes the evidence threshold on the dev unanswerables only; with 5 items one odd question can move the threshold. The unanswerable kinds differ: period not in corpus, company not in corpus, topic never discussed, figure not disclosed, period after the corpus, guidance that is never given, monthly figure (only quarterly reported), executive pay (not in these documents).
- **Alternative considered:** keeping the spec proportions exactly (5 dev / 10 test), which gives a less stable threshold.

## 2026-11-01: Gold answers may only state numbers their quotes contain
- **Decision:** `EvalGoldAnswerNumbersTest` fails if a gold answer contains a number that is not in that item's quotes (years, Qn and FYnnnn labels ignored). Runs in CI because it needs no database.
- **Reason:** a wrong number in a gold answer makes the correctness score unfair without anyone noticing. On the first run it found two answers that stated more than their quotes showed (q002 constant-currency growth, q011 period end date); both quotes were extended to the full source sentence.

## 2026-11-01: Test split has 50 items (E2.3)
- **Decision:** q035-q084, 21 single_fact, 13 multi_quarter, 11 qualitative, 5 unanswerable. Whole dataset: 84 items, 32 / 21 / 17 / 14 (spec 11.1 asks for at least 80 with 30 / 20 / 15 / 15). Test items use different facts and quotes from dev, and cover all four document types, including two facts that only appear in 10-K filings.
- **Reason:** keeps the spec proportions within one or two items per category after moving 4 unanswerable items to dev (see the entry above).
- **Rule:** test questions are not run against the system until the final evaluation; nothing is tuned on them.

## 2026-11-02: Testcontainers for database tests (E3.1)
- **Decision:** added three test-scope dependencies, versions managed by Spring Boot 4.1.2 (Testcontainers 2.0.5): `spring-boot-testcontainers`, `testcontainers-junit-jupiter`, `testcontainers-postgresql`. New DB tests start their own `pgvector/pgvector:pg16` container and connect through `@ServiceConnection`. Approved by Aum before adding (listed in spec section 4).
- **Reason:** retrieval tests need exact, hand-made rows. A throwaway container gives that without touching the ingested corpus in the local database, and it runs the same way in CI.
- **Alternative considered:** the local Docker database inside a rolled-back transaction (no new dependency, but the test data would mix with the real corpus and one mistake could delete it).
- **Note:** older DB tests (SchemaMigrationTest, EvalDatasetQuoteCheckTest) still use the local database; that is fine and unchanged.

## 2026-11-02: Vector search query design (E3.1)
- **Decision:** `VectorSearchRepository.search(queryEmbedding, filters, limit)` builds `WHERE ticker IN (?..) AND (fiscal_year, fiscal_quarter) IN ((?, ?)..) AND doc_type IN (?..)` from fixed SQL pieces, leaving out empty filters; all values are bound parameters. It orders by the `distance` alias (`embedding <=> CAST(? AS vector)`), so the query vector is sent once. Ranks are 1..n after filtering. Before the query it runs `SET LOCAL hnsw.iterative_scan = strict_order` inside a read-only transaction.
- **Reason for iterative scan:** without it the HNSW index returns about 40 nearest rows (`hnsw.ef_search`) and the filter is applied afterwards, so a narrow filter (one ticker and one quarter is about 1/36 of the corpus) could return almost nothing. Iterative scan (pgvector 0.8+) keeps searching until the limit is filled; `strict_order` keeps exact distance order. A test checks the pgvector version is at least 0.8.
- **Alternative considered:** one static query with `(? IS NULL OR ticker = ANY(?))` conditions (simpler code, but worse plans once Postgres switches to a generic plan), or always exact search without the index (correct, but ignores the HNSW index the spec asks for).
- **Reuse:** `FiscalPeriod` (eval package) and `DocumentStore.toVectorLiteral` (now public) are reused instead of duplicated.

## 2026-11-02: Keyword search matches ANY word, not ALL words (E3.2)
- **Decision:** `KeywordSearchRepository` still builds the query with `websearch_to_tsquery('english', ?)` (spec section 8), but rewrites its top-level ` & ` to ` | `, so a chunk needs at least one word of the question. `ts_rank_cd` then ranks chunks with more of the words, closer together, higher. Quoted phrases stay phrases (they use `<->`). A minus at the start of a word is removed first, because websearch syntax reads it as NOT and NOT combined with OR matches almost everything. Ties are broken by chunk id so results are repeatable.
- **Reason:** with plain AND a whole question must have every word in one chunk. Checked on Postgres 16: "What was Azure revenue growth in Q1 FY2027?" gives `'azur' & 'revenu' & 'growth' & 'q1' & 'fy2027'` and matches 0 of the 5 test chunks; with OR the Azure chunk ranks first. Users type questions, not keyword lists, so AND would leave keyword search empty most of the time and hybrid search would quietly become vector-only.
- **Known limit:** `ts_rank_cd` has no IDF, so a common word repeated in a chunk ("cloud" twice) can outrank a rare exact term (a product name) when both are in the question. Vector search and RRF balance this; E3.6 will show whether it matters on dev.
- **Alternative considered:** plain AND as the spec line reads literally (precise, but almost always empty for real questions), or `plainto_tsquery` (also AND, and loses phrase support).

## 2026-11-02: One shared Testcontainers database for all DB tests (E3.2)
- **Decision:** `PgvectorContainerTest` (test base class) starts one pgvector container in a static block and exposes it with `@ServiceConnection`. Vector and keyword search tests extend it and share one container and one Spring context. It also holds the fixture helpers (`clearDatabase` with the safety guard, `insertChunk`, `vector`). `testcontainers-junit-jupiter` was removed again: this pattern does not use `@Testcontainers`/`@Container`.
- **Reason:** with `@Container` per test class, each class would start its own container (slower), and Spring's cached context could point at a container that was already stopped. SQL pieces shared by both repositories moved to `ChunkSql` (columns, filter conditions, row mapping).

## 2026-11-02: RRF fusion as a static pure function (E3.3)
- **Decision:** `RrfFusion.fuse(vectorHits, keywordHits, rrfK, limit)` is a static method with no Spring or database. Score = sum of 1 / (rrfK + rank) over the lists a chunk is in (rrfK = 60 from `earningslens.retrieval.rrf-k`). Chunks are matched by chunk id; if one list repeats a chunk, only its best rank counts. Equal scores are ordered by the chunk's best single rank, then by chunk id, so the output never changes for the same input. `FusedHit` keeps the vector rank, keyword rank and vector similarity, so the evidence threshold (E3.7) and the eval reports can use them.
- **Reason:** the roadmap asks for a pure function; a static method is the simplest form and is tested without a database, so it runs in CI. Raw scores are not mixed because cosine distance and ts_rank_cd are on different scales.

## 2026-11-02: Query parser and period resolver conventions (E3.4)
- **Split:** `QueryParser` (pure, no database) finds tickers through `CompanyDirectory` (companies.yaml aliases, whole-word, case-insensitive) and period references. `PeriodResolver` turns them into `PeriodTarget`s (company + quarter) using `PeriodCatalog` (`JdbcPeriodCatalog`: distinct periods in `documents`). Tests use the real companies.yaml and an in-memory copy of the corpus periods.
- **Per company targets, not one period set:** the same words mean different quarters per company ("latest quarter" is MSFT FY2027 Q1 but GOOGL FY2026 Q3; September 2026 is MSFT FY2027 Q1 but GOOGL FY2026 Q3). A flat ticker set times a period set would wrongly add pairs such as MSFT FY2026 Q3 to "Microsoft and Alphabet, latest quarter". E3.5 should therefore count targets (pairs), not periods, for the "2 or more periods" rule.
- **Fiscal labels vs calendar dates:** "Qn YYYY", "Qn FYYYYY", "2Q26", "nth quarter of (fiscal) YYYY", "first half of 2026" are the company's own fiscal labels (what the filings and calls use). Month names ("December 2025", "quarter ended September 30, 2026") and "calendar Qn YYYY" / "CQn YYYY" are calendar dates, converted per company with `fiscal-year-end-month`.
- **Bare years are ignored:** "2026 capex outlook", "full-year 2026 guidance", "CapEx for 2027" and "FY2026 revenue" are usually the topic (guidance for a year), not the quarter to search. Treating them as periods would filter out the call where the guidance was given.
- **Explicit vs derived:** explicitly named quarters for a named company are kept even if not in the corpus and reported in `missing` (dev q026, q030), so E3.5 can abstain instead of answering from another quarter. Derived periods (latest, last N, a quarter without a year = its latest occurrence, each quarter of a year, previous quarter, year ago, quarters after "since") only come from the corpus. With no company named, only pairs in the corpus are kept; if none exist, all explicit pairs are reported missing.
- **Ranges:** "from X to Y", "X through Y", "between X and Y", "Q2 to Q4 of fiscal 2026", "first three quarters of 2026", "since X" expand to every quarter in between. "X and Y" / "X vs Y" without "between" is two quarters, not a range. Ranges are capped at 12 quarters.
- **Pattern order:** most specific first; each match is blanked out of the working text so looser patterns cannot match the same words again.
- **Tested:** 53 cases in `src/test/resources/retrieval/query-cases.txt` (dev questions marked; no test-split questions), plus calendar conversion, alias boundaries and year spellings.
- **Known limits:** a quarter without a year always means its latest occurrence, so "in Q3, what did Meta say about Q4 guidance?" also targets FY2025 Q4. Unknown companies (Amazon, Nvidia) are not detected; the evidence threshold (E3.7) has to catch those. Doc types are not parsed from the question ("on the call").

## 2026-11-02: Retriever rules (E3.5)
- **Modes:** `RetrievalMode` A to D as in spec 11.4. Explicit filters (UI or eval item) apply in every mode; parser filters and per-period retrieval only in C and D; the min-similarity check only in D. `earningslens.retrieval.mode: D` is the API default; eval runs pass their own mode. Until E3.7 tunes `min-similarity` (now 0.0), D behaves like C.
- **Explicit filters override the parser per field:** explicit tickers replace parsed tickers, explicit periods replace parsed periods (as explicit fiscal quarters, so a missing one is reported), doc types only come from explicit filters.
- **Per-period trigger counts company + quarter targets** (see the E3.4 entry). Two or more: one search per target with `k-per-period` (3) chunks, then results take turns by rank (best of each target first, targets in ticker and period order) and are re-numbered 1..n, so a later quarter is never pushed to the end of the prompt. One target: one search filtered to that company and quarter with `k` (8). None: one search with only the named tickers.
- **Cap at `max-periods` (4):** companies take turns, newest quarter first, so "Microsoft and Alphabet over the last three quarters" (6 targets) keeps 2 quarters of each instead of dropping a company. Left-out targets are returned in `skippedTargets`.
- **Abstain before spending anything:** if every period asked for is outside the corpus (`onlyMissingPeriods`), the retriever returns `PERIOD_NOT_IN_CORPUS` without embedding the question. In C as well as D, because it comes from the parser, not from the threshold.
- **Threshold in D:** best cosine similarity over every vector hit of every search; below `min-similarity` gives `LOW_SIMILARITY`. The chunks are still returned so eval reports can show what was found.
- **Dedupe:** two chunks are overlapping neighbours if they are in the same document, their chunk indexes differ by 1, and the last 60 characters of the earlier chunk (whitespace collapsed) appear in the later one, which is how the chunker's sentence overlap looks. The better-ranked one is kept. Each search fuses `2 x limit` candidates before dedupe, so dropping a neighbour still leaves `limit` chunks.
- **Query embedding:** through a `QueryEmbedder` interface (bean wraps `EmbeddingService`, so retries and the dimension check are shared with ingestion). Tests use a fake, so they make no OpenAI calls.

## 2026-11-02: Retrieval-only eval harness (E3.6)
- **Runner:** `EvalRunner` (profile `eval`, no web server) with `EvalProperties` (`--eval.task`, `--eval.config`, `--eval.split`, `--eval.confirm`, `--eval.label`). It prints the embedding cost estimate (question tokens x `embedding-price-per-million-tokens`, 0.02 USD per 1M for text-embedding-3-small, checked on the OpenAI model page 2026-11-02) and sends nothing unless `--eval.confirm=true`. Each question is embedded once and reused for every config, so A, B and C on dev cost 34 embeddings.
- **Test split refused:** retrieval-only runs exist for tuning, so `--eval.split=test` is rejected. The test split is run once, with all configs, in E5.4.
- **Metrics:** as spec 11.2, in `RetrievalMetrics` (pure, unit-tested). A hit is a chunk containing the gold quote after `TextNormalizer` normalisation, from any document. MRR uses the final rank in the retriever's output (for per-period results, after the turn-taking order). Period coverage counts company + quarter pairs from the gold evidence and is pooled over the multi_quarter items (covered pairs / required pairs), not averaged per item. Unanswerable items are left out of recall and MRR; their best similarity and abstention reason are listed for E3.7.
- **Recall@k is not at equal k:** config C returns up to 12 chunks (4 targets x 3) for multi-quarter questions, A and B always 8. The report shows "avg chunks" next to recall so this is visible.
- **Reports:** `eval/reports/<date>-retrieval-<configs>-<split>[-<label>].json` (everything, including each item's retrieved chunks) and `.md` (overall table, per-category table, missed quotes per config, unanswerable similarity table). `latest.json` is not touched: it is for the full eval (spec 11.5).

## 2026-11-02: First dev retrieval run and dedupe redefined (E3.6 tuning)
- **Baseline (dev, k 8, k-per-period 3, chunks 600/100):** recall@k all quotes / any quote / MRR / period coverage: A 0.440 / 0.600 / 0.331 / 0.926, B 0.400 / 0.480 / 0.347 / 0.889, C 0.520 / 0.640 / 0.403 / 1.000. Report `eval/reports/2026-11-02-retrieval-ABC-dev.md`.
- **Diagnostic added:** for every gold quote the report now replays C's search inside the quote's own quarter and shows the gold chunk's vector rank (whole quarter and real top 30), keyword rank, fused rank and rank after dedupe.
- **Findings:** (1) the approximate HNSW search is not losing chunks: top-30 vector ranks equal whole-quarter ranks. (2) Dedupe removed gold chunks that fused at rank 4 (q021) and 2 (q025): neighbouring chunks share only the chunker's ~100-token overlap, so dropping one throws away ~500 tokens of text only it contains. (3) Many gold chunks fuse at ranks 9 to 14 in their quarter (q001, q008, q014, q015, q018, q019, q022): k 8 and especially k-per-period 3 are tight. (4) For Meta press-release figure sentences (q016, q018) vector ranks are 84 to 122 while keyword ranks are 1 to 16: the embedding handles these chunks badly (candidate for a chunk-size experiment later).
- **Decision:** dedupe only drops a neighbour that is a near-duplicate: the longest end of the earlier chunk found in the later one must be at least half of the shorter chunk. Ordinary neighbours (about 1/6 shared) are both kept. This keeps the spec rule (neighbours that overlap) but reads "overlap" as "mostly the same text", which is what the rule is for.
- **Next:** `--eval.sweep` compares k x k-per-period settings (8x3, 12x4, 16x5) in one run; choose from dev only.

## 2026-11-02: k sweep on dev (E3.6 tuning)
- **Run:** `--eval.sweep=8x3,12x4,16x5` with the near-duplicate dedupe. Reports `eval/reports/2026-11-02-retrieval-ABC-dev-k8-kpp3.md`, `-k12-kpp4.md`, `-k16-kpp5.md`.

- **Cause seen in the diagnostic:** per-period searches still use the whole question, including the period words ("in each of the first three quarters of 2026"). ## 2026-11-02: Rejected: removing period words from per-period searches (E3.6 tuning)
- **Tried:** for per-period searches, search with the question minus the words the parser recognised as periods ("What was Meta's revenue in each of the first three quarters of 2026?" became "What was Meta's revenue?").
- **Result on dev (config C):** worse. 8x3 recall all / any went from 0.600 / 0.720 to 0.560 / 0.640; 16x5 from 0.720 / 0.880 to 0.720 / 0.800. Diagnostic: q014 gold keyword ranks fell from 15-27 to 66-75, q017 fused ranks from 2-6 to 10-18.
- **Why:** the gold sentences sit under press-release headings such as "Fourth Quarter Results" or "First Quarter 2026 Financial Highlights". The period words match those headings, so they lift the right section even inside a search filtered to one quarter. The shortened questions were too generic.
- **Decision:** reverted; per-period searches keep the full question. The code was removed rather than kept behind a switch.

## 2026-11-02: Chosen retrieval settings: k 16, k-per-period 5 (E3.6)
- **Decision:** `earningslens.retrieval.k: 16`, `k-per-period: 5` (spec defaults 8 and 3), max-periods stays 4, so at most 20 chunks per question.
- **Evidence (dev, config C, full question, near-duplicate dedupe):** recall all / any / MRR 0.720 / 0.880 / 0.440 at 16x5, against 0.640 / 0.760 / 0.432 at 12x4 and 0.600 / 0.720 / 0.429 at 8x3. All single_fact and qualitative gold quotes are retrieved at 16x5; multi_quarter is the weak category (recall any 0.625, all 0.125).
- **Cost of the choice:** more prompt text in Phase 4, roughly 20 x 600 = 12k input tokens per multi-quarter question at most, about 0.002 USD with gpt-4o-mini. MRR barely changes with k, so the gold chunk is not pushed further down for questions that were already found.
- **Not done:** chunk size stays 600/100. The remaining misses are mostly Meta press-release figure sentences that the embedding ranks around 100 in their quarter (q016, q018) and Microsoft segment figures that keyword search ranks low (q014). A chunk-size experiment needs a re-ingest and a quote re-check; parked unless Phase 5 shows these questions failing.

## 2026-11-02: Evidence threshold min-similarity 0.531 (E3.7)
- **Data:** config C at k 16 / k-per-period 5 on dev, best vector similarity per question (report `eval/reports/2026-11-02-retrieval-C-dev-threshold.md`). Unanswerable: q026, q030, q031 abstain anyway (period not in corpus); q034 0.504, q028 0.517, q033 0.557, q027 0.576, q029 0.582, q032 0.711. Lowest answerable: q009 0.545, q004 0.566, q005 0.587, then 0.634 and up. The two groups overlap, so no threshold separates them.
- **Candidates (abstention as the prediction for "unanswerable"):** 0 (off): precision 1.00, recall 0.33, F1 0.50, no answerable blocked. **0.531: precision 1.00, recall 0.56 (5/9), F1 0.71, no answerable blocked.** 0.584 (highest F1): precision 0.80, recall 0.89 (8/9), F1 0.84, but blocks 2/25 answerable (q004, q009; false-abstention rate 8%).
- **Decision (Aum):** 0.531. It never blocks an answerable dev question. 0.584 sits 0.002 to 0.003 from items on both sides (q029 0.582, q005 0.587), which is too fine to trust from 34 questions; and wrongly refusing a question the corpus can answer is worse for users than letting an unanswerable one reach the LLM, which can still answer INSUFFICIENT_EVIDENCE (Phase 4).
- **Known gap:** q032 (monthly revenue, 0.711) cannot be caught by any similarity threshold without blocking most answerable questions; it is left to the LLM's own abstention. Revisit the threshold in Phase 5 if the combined abstention numbers suggest it.

## 2026-11-02: Prompt builder source format (E4.1)
- **Numbering:** sources are numbered by list position (1..n) in the order the retriever returns them, so every valid marker `[n]` points to an existing source. `Prompt` keeps the chunk list in the same order for the citation validator (E4.3).
- **Label:** `TICKER | FYyyyy Qn | DOC_TYPE`, then `p.4` (or `p.4-5` for a chunk spanning pages) when the chunk has page numbers (PDF), otherwise `section: ...` when it has a section, otherwise nothing. The section is put on one line and cut to 200 characters, the same limit as the chunker's `Section:` header line.
- **Body without repeated headers:** every chunk starts with the chunker's `[TICKER | FYyyyy Qn | DOC_TYPE]` line, and the section line repeats the label for HTML chunks. Both are removed from the body because the label already says the same thing (saves tokens, and a bracketed line next to `[n]` markers could confuse the model). The `Speaker:` line is kept, and so is the `Section:` line when the label shows pages instead.
- **System prompt:** `src/main/resources/prompts/answer-system.txt`, text exactly as spec 9.1, read once at startup (CRLF converted to LF so a Windows checkout gives the same prompt).
- **Guards:** a blank question or an empty source list is rejected; with no sources the answer service (E4.2) abstains without calling the model.

## 2026-11-04: Answer service (E4.2)
- **Model behind an interface:** `ChatLlm` (one method: system + user message in, `LlmReply` out). `OpenAiChatLlm` is the real one; tests use a lambda fake, so no OpenAI calls in CI. Same pattern as `QueryEmbedder`.
- **Options:** in Spring AI 2.0.1, options sent with a request replace the model's defaults completely (`OpenAiChatModel.buildRequestPrompt`, checked in the 2.0.1 sources). So `OpenAiChatLlm` copies the defaults (`mutate()`) and sets only model, temperature 0 and max 700 output tokens from `earningslens.llm`. This keeps the default 60 s request timeout.
- **No retries for chat:** retries are set once on the OpenAI client (`spring.ai.openai.max-retries: 0`). A failed chat call goes straight to `LlmUnavailableException` (503 in E4.7) so a user is not kept waiting. Revisit for the Phase 5 eval run if 429s appear (retry per eval item there, not in the API).
- **Model not called when retrieval abstains** (`PERIOD_NOT_IN_CORPUS`, `LOW_SIMILARITY`) or finds no chunks (`NO_SOURCES`): no cost.
- **INSUFFICIENT_EVIDENCE detection:** the reply counts as an abstention if, after trimming whitespace, quotes, backticks, asterisks and a final full stop, it is the token or starts with the token followed by a non-word character. The token in the middle of an answer does not count (left to the validators).
- **Abstention message** (spec 9.2): lists the company + quarter pairs searched, plus quarters not in the corpus and quarters skipped by the max-periods cap. For `PERIOD_NOT_IN_CORPUS` it names the missing quarters instead.
- **Empty reply** is treated as an LLM error, not an abstention.
- **Recorded per answer:** model name reported by the API (falls back to the configured name), prompt and completion tokens (null if not reported, or when the model was not called), and `truncated` when the finish reason is LENGTH (hit the 700-token limit).

## 2026-11-04: Citation validator (E4.3)
- **Marker forms read:** `[2]`, `[1][3]`, `[1] [3]` and `[1, 3]`. Only 1 to 3 digits, so `[2026]` is not a marker. Out-of-range markers (0 or above the source count) are removed with one warning each (spec 9.2). Each group is rewritten as `[1][3]` with repeats inside the group dropped, so the frontend only handles one form. The same marker in different sentences is kept.
- **Output per sentence:** `CitationCheck` keeps every counted sentence with its own markers, not just an uncited count. The Phase 5 judge needs sentence + chunk pairs for citation precision (spec 11.2); the API uses `citedMarkers` (each valid marker once, in order of first use) for the citations list, and E4.4 uses it to know which sources were cited.
- **Sentence splitting:** per line (bullets and per-quarter sections split naturally), then at `. ! ?` followed by whitespace and a capital, digit, quote, bracket, `$` or markdown. Not after common abbreviations (Mr., Dr., Inc., U.S., e.g., i.e., vs., etc.). Decimals like `3.2` never split (no space). A marker written after the full stop (`... billion. [2] Next`) is moved back to the sentence before it.
- **Sentences that do not need a citation:** headings (ending in `:`, starting with `#`, or only bold text such as `**FY2026 Q1**`) and fragments under 3 words. Everything else without a marker counts as uncited; one warning gives the count (`2 of 7 sentences have no citation.`).
- **No new dependency:** plain Java regex.

## 2026-11-04: Number grounding check (E4.4)
- **Formats read:** `1,234`, `12.5%`, `12.5 percent`, `$3.2 billion`, `3.2bn`, `$3.2B`, `50 basis points` / `50 bps`, `2 percentage points`. Each number becomes a value plus a kind (amount, percent, basis points). Amounts are compared after applying the scale word, so `$3.2 billion` = `3,200 million`.
- **Rounding:** an answer number matches if the source value rounds to it at the answer's precision (half a unit of its last digit), so `$70.1 billion` matches a table cell `70,066`. An answer more precise than the source (`$32.95 billion` vs `$32.9 billion`) is not grounded.
- **Table cells:** a source number with no unit is tried as is, as thousands and as millions, because 10-Q and press-release tables say "($ in millions)" in a header row, not next to the number. This can let a rounded figure match by coincidence; accepted, since the check is a warning and the table case is common.
- **Kinds must match:** a percent only matches a percent, basis points only basis points.
- **Only cited sources count** (spec 9.2): the sources come from `CitationCheck.citedMarkers`, after invalid markers were removed.
- **Not checked in the answer:** citation markers, standalone years 1990 to 2100, digits inside words (FY2026, Q1, gpt-4o), and plain whole numbers under 10 (list numbering, "3 segments"). Dates like "June 30" are still checked; they usually appear in the source too.
- **Output:** `GroundingCheck` lists every number mention with grounded yes/no (for the spec 11.2 grounding rate) and one warning per distinct unmatched number (`Not found in the cited sources: 47%`).

## 2026-11-04: Chat endpoint (E4.5)
- **Layers:** `ChatController` (HTTP + `@Valid` only) -> `ChatService` (retrieve -> answer -> citation check -> number check -> response -> query_log). DTOs are records in `api.dto`. Validation: question 3 to 500 characters; filters optional, and each list inside them optional (null is read as empty); quarters 1 to 4; unknown doc types and broken JSON are 400.
- **groundingWarnings holds both kinds of warning:** the spec response has one warnings list, so citation warnings (removed markers, uncited sentences) and number warnings go in it together, citation warnings first.
- **Citations:** one per valid marker used in the answer, in order of first use, with the marker number the model used (not renumbered). `page` is the chunk's first page. `sourceUrl` comes from the documents table (one `findAllById` per request). `snippet` is the first 300 characters of the chunk text with the chunker's header lines (`[...]`, `Section:`, `Speaker:`) removed, since the citation already has those fields.
- **appliedFilters:** companies and quarters the retriever actually targeted (including asked-for quarters not in the corpus); if no quarter was targeted, the requested companies, else the companies the parser found in the question (modes C and D). Doc types as requested.
- **model** is the model that answered, or null when the model was not called (retrieval abstained).
- **Abstained answers:** no citations, no warnings; the checks are not run.
- **query_log:** one row per successful request: stripped question, applied filters (JSON), ALL retrieved chunk ids (not only cited ones), final answer text, abstained, latency, token counts (null when the model was not called). No IP or personal data. A failed log write is logged as a warning and does not fail the request. Failed requests (LLM error) are not logged yet; revisit with E4.7 error handling.
- **Manual calls:** `backend/http/chat.http` (IntelliJ HTTP Client) with dev question q001 only. Cost of one call checked on 2026-11-04: gpt-4o-mini $0.15 per 1M input and $0.60 per 1M output tokens; about 10.5k input + up to 700 output tokens = about 0.2 US cents.

- **ProblemDetail everywhere:** `GlobalExceptionHandler` extends Spring's `ResponseEntityExceptionHandler`, which already turns MVC errors (unreadable JSON 400, unknown URL 404, wrong method 405, `ResponseStatusException`) into RFC 7807 bodies. - **Client IP:** `request.getRemoteAddr()` only; X-Forwarded-For is never read by our code, because a client can fake it. In prod, `server.forward-headers-strategy: framework` makes Spring use the proxy's forwarded address (Azure Container Apps), so the limit sees the real client.

## 2026-11-04: LLM judge (E5.1)
- **Judge model: gpt-4.1** (`eval.judge.model`), chosen by Aum. Alternatives: gpt-4o-mini (cheapest, but it is the answer model, so it would grade its own answers) and gpt-4.1-mini (cheaper, weaker at subtle unsupported claims). List prices checked 2026-11-04: gpt-4.1 $2.00 / $8.00 per 1M input / output tokens. Estimated cost for all of Phase 5 (about 270 judged answers): about 4 US dollars. Temperature 0.
- **One judge call per answer** does all three metrics (claims for faithfulness, correctness 1 to 5, one entry per sentence/marker pair for citation precision). Three separate calls would triple the cost and repeat the same sources three times.
- **The rubric file is the prompt:** everything below "## Judge prompt" in `eval/judge-rubric.md` is sent word for word as the system message, so the rubric validated against human labels in E5.2 is exactly what the judge reads. Changes are logged in the rubric's change log.
- **Structured output:** the request uses OpenAI JSON schema output in strict mode (Spring AI 2.0.1 `OpenAiChatModel.ResponseFormat`, type JSON_SCHEMA, checked in the 2.0.1 source: the string is the schema itself). No new dependency. `JudgeResponseParser` then checks what a schema cannot: score 1 to 5, non-empty reasons, at least one claim, a supported claim names a source, claims only name sources that were shown, and the citations list answers exactly the pairs sent, once each, in order.
- **Invalid output:** one retry with the error appended to the message (`eval.judge.max-attempts: 2`), then `JudgeOutputException` stops the run. Scores are never guessed or filled in.
- **What the judge sees:** question, gold answer, the answer after CitationValidator, only the sources the answer cites (under their original numbers, labelled like the answer prompt), each sentence with its markers, and the list of pairs. Uncited sources are left out: faithfulness is "supported by the cited sources" (spec 11.2), and it keeps the input small.
- **Faithfulness is checked against all cited sources of the answer,** not only the markers on the claim's own sentence. Whether a marker sits on the right sentence is measured separately by citation precision. This keeps the two metrics independent: a true fact with a misplaced marker lowers citation precision, not faithfulness.
- **Arithmetic and rounding:** a figure derived from source figures by a sum, difference or percentage change, or rounded to the precision shown, counts as supported.
- **Abstentions are not judged;** they are scored by the abstention metrics (spec 11.2).
- **Smoke run:** `--eval.task=judge-sample` (dev only) answers `eval.judge.sample-ids` (q001 single_fact, q015 multi_quarter, q021 qualitative) with config C, judges them and writes `eval/reports/{date}-judge-sample-dev.json`. The worst-case cost is printed first and `--eval.confirm=true` is required.
- **Answer model prices** added to the eval settings for cost reporting: gpt-4o-mini $0.15 / $0.60 per 1M tokens (checked 2026-11-04).
- `PromptBuilder.label` and `body` are now public so the judge shows sources exactly as the answer model saw them.

## 2026-11-04: Full metrics and the cost guard (E5.3)
- **One task for everything:** `--eval.task=full --eval.config=C --eval.split=dev --eval.confirm=true` runs every item through the same Retriever, AnswerService, CitationValidator and NumberGroundingCheck as the chat API, then the judge (rubric v2), and writes `eval/reports/{date}-{config}-{split}[-label].json` and `.md` per config (spec 11.5), plus `{date}-ablation-{split}[-label].md` when several configs run (needed for E5.4). Test split still refused; E5.4 opens it for one run.
- **Correctness counts every item:** answers get the judge's 1 to 5; abstentions get 5 on unanswerable items and 1 on answerable items (rubric task 3: "says the information is not available when the reference gives it" is a 1). Otherwise a config that declines more often would avoid low scores and look better. The judge-only mean over answered answerable items is reported too. Alternative: judge-only mean (rejected for the reason above).
- **Faithfulness** = mean of per-answer supported / claims, plus the share of fully faithful answers. **Citation precision and number grounding** are pooled over all pairs / numbers (micro averages), so long answers count in proportion to how much they claim.
- **Abstention:** precision = right abstentions / all abstentions; recall = unanswerable items abstained / unanswerable items; false-abstention rate = answerable items abstained / answerable items. Abstention reasons are counted.
- **Operations:** latency = retrieval + answer (as ChatService measures it, judge excluded), p50 / p95 by nearest rank; cost per query = question embedding (skipped when retrieval stops before embedding) + answer-model tokens at config prices; judge cost reported separately (it is not part of a user query).
- **Errors:** an item whose answer model or judge fails (after the judge's one retry) is left out of every metric and listed in the report. No retries for the answer model (as in the API).
- **Cost guard:** the typical and worst-case cost are printed before anything is sent; nothing is sent without `--eval.confirm=true`. Typical sizes come from E5.2 (answer prompt about 9k tokens; judge about 3k in, 600 out).
- **latest.json is not written by dev runs:** the UI and README only show the final test-split numbers (E5.4).
